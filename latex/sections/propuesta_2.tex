\section{Propuesta 2}
\label{sec:propuesta_2}

    El escenario de caos del sistema base (Sección~\ref{sec:sistema_base_pruebas_de_chaos}) mostró que una única request inválida
    alcanza para tirar el proceso de la API y que, a partir de ese momento, el servicio queda indisponible hasta que alguien lo
    levante manualmente: no existe ningún mecanismo de detección ni de recuperación de fallas.
    Si bien la causa raíz (la falta de validación de las requests) debe corregirse, no es posible garantizar que no existan
    otras fallas que terminen el proceso. Por eso la propuesta 2 no apunta a evitar la falla, sino a acotar el tiempo que el
    servicio permanece caído cuando esta ocurre.

    Para ello aplicamos las siguientes tácticas de disponibilidad:

    \begin{itemize}
        \item \textbf{Heartbeat (detección de fallas):} la API envía cada 1 segundo un datagrama UDP a cada uno de los watchdogs indicando que está viva.
        \item \textbf{Monitor / watchdog (detección de fallas):} se agrega un componente independiente de la API que, si no recibe un heartbeat de la API durante 3 segundos, la considera caída.
        \item \textbf{Restart (recuperación):} al detectar la caída, el watchdog reinicia el contenedor de la API a través de la API de Docker (montando \texttt{/var/run/docker.sock}).
        \item \textbf{Redundancia activa del monitor:} para que el watchdog no sea un nuevo punto único de falla, se despliegan tres instancias. Solo una de ellas (el líder) actúa sobre la API; el líder se elige mediante el algoritmo \textit{Bully} y el resto le envía heartbeats. Si el líder deja de responder durante 3 segundos, se inicia una nueva elección.
    \end{itemize}

    Cabe destacar que esta propuesta se implementó sobre el sistema base y no sobre la propuesta 1, de modo que los resultados
    solo reflejan el efecto de estas tácticas y sean comparables contra el sistema base.

    \subsection{Impacto en los QA}
    \label{sec:propuesta_2_impacto_en_los_qa}

        \subsubsection{Disponibilidad}
        \label{sec:propuesta_2_disponibilidad}

        Es el QA que la propuesta busca mejorar. Frente a fallas que terminan el proceso (\textit{crash}), el tiempo de
        indisponibilidad pasa de ser indefinido a estar acotado por el tiempo de detección (hasta 3 segundos de timeout más
        1 segundo del período de chequeo) sumado al tiempo de reinicio del contenedor. Como se verá en las
        \hyperref[sec:propuesta_2_pruebas_de_chaos]{pruebas de caos}, esto se traduce en caídas de pocos segundos en lugar de la
        pérdida total del servicio.

        Sin embargo, el heartbeat solo indica que el proceso está vivo y que su event loop avanza, no que responda en tiempo
        aceptable. Una degradación de performance como la causada por el log (Sección~\ref{sec:sistema_base_pruebas_de_soak})
        no es detectada, y por lo tanto no esperamos mejoras en los escenarios de estrés y resistencia.

        El valor de 3 segundos para el timeout es un tradeoff: reducirlo disminuye el tiempo de recuperación, pero aumenta
        el riesgo de falsos positivos. Dado que el heartbeat se envía desde el mismo event loop que atiende las requests, una
        operación síncrona larga (por ejemplo, serializar un log muy grande) podría retrasarlo y provocar el reinicio de una API
        que en realidad seguía funcionando, descartando todas las requests en curso.

        \subsubsection{Confiabilidad}
        \label{sec:propuesta_2_confiabilidad}

        El reinicio no resuelve la pérdida de datos. El estado se mantiene en memoria y se persiste a disco cada 1 segundo
        (ver Listado~\ref{lst:save}), por lo que ante un crash se pierden las operaciones realizadas desde el último guardado,
        además de las requests que estaban siendo procesadas. Como se utiliza \texttt{docker restart} y no se recrea el
        contenedor, el sistema de archivos se conserva y la API retoma desde el último estado guardado. La evidencia de esto
        se observa en la Figura~\ref{fig:comparacion_propuesta_2_sistema_base_chaos_endpoint_response_time}, donde el tiempo de
        respuesta de \texttt{/log} sigue creciendo después de cada reinicio en lugar de volver a cero.

        Además, la táctica no corrige la causa de la falla: la request inválida sigue tirando el proceso cada vez que llega.
        La propuesta mitiga el efecto, pero la validación de las requests sigue siendo necesaria.

        \subsubsection{Performance}
        \label{sec:propuesta_2_performance}

        El único trabajo agregado a la API es el envío de tres datagramas UDP por segundo, que consideramos despreciable frente
        al procesamiento de las requests. Los watchdogs corren en contenedores separados, por lo que no compiten directamente
        con la API, aunque sí comparten el host. En las pruebas de estrés y resistencia no se observan diferencias atribuibles
        a la táctica.

        \subsubsection{Seguridad}
        \label{sec:propuesta_2_seguridad}

        Para poder reiniciar la API, los watchdogs montan el socket de Docker del host. Esto les otorga control total sobre
        el daemon de Docker, que es equivalente a tener acceso de administrador al host. Una vulnerabilidad en el watchdog
        compromete todo el servidor. Además, los mensajes UDP entre la API y los watchdogs no están autenticados, por lo que
        cualquier proceso dentro de la red podría enviar heartbeats falsos (enmascarando una caída) o mensajes de elección.

        \subsubsection{Escalabilidad y modificabilidad}
        \label{sec:propuesta_2_escalabilidad_y_modificabilidad}

        El nombre del contenedor supervisado (\texttt{exchange-api-1}) y la lista de watchdogs están fijos en el código. Esto
        impide escalar horizontalmente la API sin modificar el watchdog, y agregar o quitar watchdogs requiere modificar tanto
        el watchdog como la API. Por otro lado, la API no conoce al watchdog más allá del envío del heartbeat, por lo que la
        lógica de supervisión puede evolucionar sin cambios en el servicio.

        \subsubsection{Simplicidad}
        \label{sec:propuesta_2_simplicidad}

        La arquitectura pasa de tener un único proceso de negocio a tener cuatro, e incorpora un algoritmo distribuido de
        elección de líder que agrega nuevos modos de falla: por ejemplo, durante una partición de red podrían existir dos
        líderes y ambos reiniciarían la API. Una alternativa más simple, como la política \texttt{restart: on-failure} de Docker,
        cubriría el caso de crash con menos componentes, pero no detectaría un proceso colgado y dejaría la recuperación atada
        al daemon de Docker del host.

    \subsection{Resultados y conclusiones}
    \label{sec:propuesta_2_resultados_y_conclusiones}

    La propuesta 2 cumple su objetivo frente a fallas que terminan el proceso: en el escenario de caos el sistema pasa de quedar
    indisponible de forma permanente a recuperarse en pocos segundos, y el volumen operado aumenta un $152\%$. El tiempo de
    recuperación observado es consistente con los parámetros configurados.

    Por otro lado, los escenarios de estrés y resistencia no muestran diferencias frente al sistema base. Esto es esperable, ya
    que el heartbeat verifica que el proceso esté vivo y no que responda en tiempo aceptable: el sistema puede estar degradado
    durante más de 20 minutos sin que el watchdog intervenga. Para cubrir este caso sería necesario un chequeo de salud a nivel
    de aplicación (por ejemplo, medir el tiempo de respuesta de un endpoint), o bien atacar la causa de la degradación como lo
    hace la propuesta 1. Ambas propuestas son complementarias.

    Los costos de la táctica son una arquitectura más compleja, con un algoritmo distribuido y tres componentes nuevos, y un
    impacto negativo en la seguridad por el acceso de los watchdogs al socket de Docker. Además, la táctica no evita la
    pérdida de las operaciones en curso ni de las que no se llegaron a persistir, y no reemplaza la validación de las requests,
    que sigue siendo necesaria para eliminar la causa de la falla.
