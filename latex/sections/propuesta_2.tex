\section{Propuesta 2}
\label{sec:propuesta_2}

    El escenario de caos del sistema base (Sección~\ref{sec:sistema_base_pruebas_de_chaos}) mostró que una única request inválida
    alcanza para terminar el proceso de la API y que, a partir de ese momento, el servicio permanece interrumpido hasta
    que alguien reinicie la API manualmente: no existe ningún mecanismo de detección ni de recuperación de fallas.
    Si bien la causa raíz (la falta de validación de las requests, ver Código~\ref{lst:request_validation}) debe corregirse, no es posible garantizar que no existan
    otras fallas que terminen el proceso. Por eso la propuesta 2 no apunta a evitar la falla, sino a acotar el tiempo que el
    servicio permanece caído cuando esta ocurre.

    Para ello aplicamos las siguientes tácticas de disponibilidad:

    \begin{itemize}
        \item \textbf{Heartbeat (detección de fallas):} la API envía cada 1s un datagrama UDP a cada uno de los watchdogs indicando que está viva.
        \item \textbf{Monitor / watchdog (detección de fallas):} se agrega un componente independiente de la API que, si no recibe un heartbeat de la API durante 3s, la considera caída.
        \item \textbf{Restart (recuperación):} al detectar la caída, el watchdog reinicia el contenedor de la API a través de la API de Docker (montando \texttt{/var/run/docker.sock}).
        \item \textbf{Redundancia activa del monitor:} para que el watchdog no sea un nuevo punto único de falla, se despliegan tres instancias. Solo una de ellas (el líder) actúa sobre la API; el líder se elige mediante el algoritmo \textit{Bully} y el resto le envía heartbeats. Si el líder deja de responder durante 3s, se inicia una nueva elección.
    \end{itemize}

    Clasificamos la redundancia del monitor como activa, y no como pasiva, porque las tres instancias procesan las mismas
    entradas en paralelo: la API envía su heartbeat a los tres watchdogs y cada uno actualiza su registro del último
    heartbeat recibido, aunque solo el líder actúe sobre la API (Código~\ref{lst:p2_redundancia}). En una redundancia pasiva,
    en cambio, solo la instancia principal procesaría las entradas y las demás recibirían actualizaciones periódicas de su
    estado.

    \begin{code}

    La consecuencia práctica es que, cuando un seguidor es elegido líder, ya conoce el estado de la API y puede comenzar a
    supervisarla de inmediato, sin necesidad de sincronizar estado con el líder anterior. Si la redundancia fuera pasiva,
    un seguidor que no hubiera recibido los heartbeats podría declarar caída a una API sana al asumir el liderazgo, o
    demorar la detección de una caída real hasta reconstruir ese estado.

    Cabe destacar que esta propuesta se implementó sobre el sistema base y no sobre la propuesta 1, de modo que los resultados
    reflejen solo el efecto de estas tácticas y sean comparables con los del sistema base.

    \subsection{Impacto en los QA}
    \label{sec:propuesta_2_impacto_en_los_qa}

        \subsubsection{Disponibilidad}
        \label{sec:propuesta_2_disponibilidad}

        Es el QA que la propuesta busca mejorar. Frente a fallas que terminan el proceso (\textit{crash}), el tiempo durante
        el cual el servicio no está disponible pasa de ser indefinido a estar acotado por el tiempo de detección (hasta 3s de timeout más
        1s del período de chequeo) sumado al tiempo de reinicio del contenedor. Como se verá en las
        pruebas de caos (Sección~\ref{sec:propuesta_2_pruebas_de_chaos}), esto se traduce en caídas de pocos segundos en lugar de la
        pérdida total del servicio.

        Sin embargo, el heartbeat solo indica que el proceso está vivo y que su event loop avanza, no que responda en un tiempo
        aceptable. Una degradación de performance como la causada por el log (Sección~\ref{sec:sistema_base_pruebas_de_soak})
        no es detectada, y por lo tanto no esperamos mejoras en los escenarios de estrés y resistencia.

        El valor de 3s para el timeout es un tradeoff: reducirlo disminuye el tiempo de recuperación, pero aumenta
        el riesgo de falsos positivos. Dado que el heartbeat se envía desde el mismo event loop que atiende las requests, una
        operación síncrona larga (por ejemplo, serializar un log muy grande) podría retrasarlo y provocar el reinicio de una API
        que en realidad seguía funcionando, descartando todas las requests en curso.

        \subsubsection{Confiabilidad}
        \label{sec:propuesta_2_confiabilidad}

        El reinicio no resuelve la pérdida de datos. El estado se mantiene en memoria y se persiste a disco cada 1s
        (ver Código~\ref{lst:save}), por lo que ante un crash se pierden las operaciones realizadas desde el último guardado,
        además de las requests que estaban siendo procesadas. Como se utiliza \texttt{docker restart} y no se recrea el
        contenedor, el sistema de archivos se conserva y la API retoma desde el último estado guardado. La evidencia de esto
        se observa en la Figura~\ref{fig:comparacion_propuesta_2_sistema_base_chaos_endpoint_response_time}, donde el tiempo de
        respuesta de \texttt{/log} sigue creciendo después de cada reinicio en lugar de volver a su valor inicial.

        Además, la táctica no corrige la causa de la falla: la request inválida sigue terminando el proceso cada vez que llega (Figura~\ref{fig:comparacion_propuesta_2_sistema_base_chaos_requests_state}).
        La propuesta mitiga el efecto, pero la validación de las requests sigue siendo necesaria.

        \subsubsection{Performance}
        \label{sec:propuesta_2_performance}

        El único trabajo agregado a la API es el envío de 3 datagramas UDP/s, que consideramos despreciable frente
        al procesamiento de las requests. Los watchdogs corren en contenedores separados, por lo que no compiten directamente
        con la API, aunque sí comparten el host. En las pruebas de estrés (Sección~\ref{sec:propuesta_2_pruebas_de_stress}) y resistencia (Sección~\ref{sec:propuesta_2_pruebas_de_soak}) no se observan diferencias atribuibles
        a la táctica.

        \subsubsection{Seguridad}
        \label{sec:propuesta_2_seguridad}

        Para poder reiniciar la API, los watchdogs montan el socket de Docker del host. Esto les otorga control total sobre
        el daemon de Docker, que es equivalente a tener acceso de administrador al host. Una vulnerabilidad en el watchdog
        compromete todo el servidor. Además, los mensajes UDP entre la API y los watchdogs no están autenticados, por lo que
        cualquier proceso dentro de la red podría enviar heartbeats falsos (enmascarando una caída) o mensajes de elección.

        \subsubsection{Escalabilidad y modificabilidad}
        \label{sec:propuesta_2_escalabilidad_y_modificabilidad}

        El nombre del contenedor supervisado (\texttt{exchange-api-1}) y la lista de watchdogs están fijos en el código. Esto
        impide escalar horizontalmente la API sin modificar el watchdog, y agregar o quitar watchdogs requiere modificar tanto
        el watchdog como la API. Por otro lado, la API no conoce al watchdog más allá del envío del heartbeat, por lo que la
        lógica de supervisión puede evolucionar sin cambios en el servicio.

        \subsubsection{Simplicidad}
        \label{sec:propuesta_2_simplicidad}

        La arquitectura pasa de tener un único proceso a tener cuatro, e incorpora un algoritmo distribuido de
        elección de líder que agrega nuevos modos de falla: por ejemplo, durante una partición de red podrían existir dos
        líderes y ambos reiniciarían la API. Una alternativa más simple, como la política \texttt{restart: on-failure} de Docker,
        cubriría el caso de crash con menos componentes, pero no detectaría un proceso colgado y dejaría la recuperación atada
        al daemon de Docker del host.

        \subsubsection{Costo y eficiencia}
        \label{sec:propuesta_2_costo_y_eficiencia}

        La propuesta agrega tres contenedores. A diferencia de la API, que tiene un límite de 1 CPU y 4 GB de memoria, los
        watchdogs no declaran límites de recursos en el \texttt{docker-compose.yml}. Como todo el sistema corre en un único
        servidor (Sección~\ref{sec:eficiencia}), un watchdog con un consumo anómalo competiría por los recursos con la API sin
        ninguna cota. Además, los watchdogs se construyen a partir de la misma imagen que la API (\texttt{build: ./app}), por lo
        que cada uno incluye el código y el estado de la aplicación aunque solo ejecuta \texttt{watchdog.js}. A la inversa,
        la dependencia \texttt{dockerode}, que solo usa el watchdog, se agrega al \texttt{package.json} de la API.

        De los tres watchdogs, solo el líder supervisa la API; los otros dos permanecen en espera y únicamente intercambian
        heartbeats con él. Este es el costo de la redundancia del monitor: dos contenedores que no aportan trabajo mientras el
        líder funcione, a cambio de que la supervisión sobreviva a su caída.

        Sobre la API, el costo es el envío de 3 datagramas UDP/s. En el escenario de carga no se observa una diferencia en el
        uso de recursos frente al sistema base ($9.68\%$ frente a $9.28\%$ de CPU promedio,
        Sección~\ref{sec:propuesta_2_pruebas_de_baseline}), por lo que la táctica no reduce la eficiencia de la API.

        Durante la prueba de carga de 40 requests por segundo, los promedios de los tres watchdogs sumaron
        un $0.32\%$ de CPU y cerca de 86 MiB de memoria. El watchdog 3, que era el líder, tuvo un consumo de CPU
        algo mayor: $0.149\%$, frente a $0.089\%$ y $0.080\%$ de los otros dos. En esta medición, el costo fue bajo,
        aunque se agregan tres contenedores sin límites de recursos configurados.

    \subsection{Pruebas de carga}
    \label{sec:propuesta_2_pruebas_de_baseline}

    Las pruebas de carga utilizan la misma configuración que en el sistema base (Sección~\ref{sec:sistema_base_pruebas_de_baseline}), de modo que los resultados sean comparables.
    Con esta carga el sistema base no presenta fallas ni caídas, por lo que el watchdog no debería intervenir y el escenario
    permite aislar el costo de la táctica en condiciones normales.

    Ambos sistemas completaron todas las requests sin fallas, con un promedio de 394 requests completadas por ventana de 10s en la propuesta 2 y de 397 en el sistema base.
    Los tiempos de respuesta son prácticamente idénticos: el P95 de \texttt{/exchange} medido en el servidor es de 719ms frente a 718ms,
    y, desde el cliente, el P95 es de 712ms en ambos casos y el P99 de 761ms frente a 759ms.
    El uso de recursos de la API también es equivalente, con un promedio de CPU del $9.68\%$ frente a $9.28\%$ y de memoria del $1.26\%$ frente a $1.25\%$.
    Esto confirma que el envío de los heartbeats no tiene un costo observable sobre la API (Sección~\ref{sec:propuesta_2_performance}).

    \subsection{Resultados y conclusiones}
    \label{sec:propuesta_2_resultados_y_conclusiones}

    La propuesta 2 cumple su objetivo frente a fallas que terminan el proceso: en el escenario de caos, el sistema pasa de quedar
    fuera de servicio de forma permanente a recuperarse en pocos segundos, y el volumen operado aumenta un $152\%$ (Figura~\ref{fig:comparacion_propuesta_2_sistema_base_chaos_currency}). El tiempo de
    recuperación observado es consistente con los parámetros configurados (Figura~\ref{fig:comparacion_propuesta_2_sistema_base_chaos_response_time}).

    Por otro lado, los escenarios de estrés y resistencia no muestran diferencias frente al sistema base. Esto es esperable, ya
    que el heartbeat verifica que el proceso esté vivo y no que responda en un tiempo aceptable: el sistema puede estar degradado
    durante más de 20m sin que el watchdog intervenga (Figura~\ref{fig:comparacion_propuesta_2_sistema_base_soak_resources}). Para cubrir este caso sería necesario un chequeo de salud a nivel
    de aplicación (por ejemplo, medir el tiempo de respuesta de un endpoint), o bien atacar la causa de la degradación como lo
    hace la propuesta 1 (Sección~\ref{sec:propuesta_1}). Ambas propuestas son complementarias.

    Los costos de las tácticas son una arquitectura más compleja, con un algoritmo distribuido y tres componentes nuevos
    (Sección~\ref{sec:propuesta_2_costo_y_eficiencia}), y un impacto negativo en la seguridad por el acceso de los watchdogs
    al socket de Docker. Además, la propuesta no evita la
    pérdida de las operaciones en curso ni de las que no se llegaron a persistir, y no reemplaza la validación de las requests,
    que sigue siendo necesaria para eliminar la causa de la falla.
