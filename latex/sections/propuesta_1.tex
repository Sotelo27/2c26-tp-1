\section{Propuesta 1}
\label{sec:propuesta_1}

    El sistema presenta una degradación principalmente por el manejo indebido del log.
    Destacamos que la posibilidad de permitir consultar el log de manera completa es la principal causa de degradación.
    Este escala con el número de operación, lo que provoca un aumento en el uso de recursos para mantenerlo, y un aumento en los tiempos de respuesta para consultarlo.
    Esto arrastra la degradación a los otros endpoints, entre ellos \texttt{/exchange}, el principalmente mencionado por los usuarios.

    Destacamos que un endpoint que permite consultarlo todo por definición no es escalable, recomendamos la implementación de paginación.
    Sin embargo, asumimos que este es un requerimiento de negocio y que las mejoras propuestas no deben alterar la firma del sistema para con los usuarios.
    Se propone desacoplar el log para que la degradación de este no afecte a los endpoints de negocio del sistema.
    Proponemos agregar un nodo dedicado, análogo a exchange-api para el manejo del log.
    Algunas optimizaciones de la implementación que consideramos que vale la pena mencionar son:

    \begin{itemize}
        \item Remplazamos el uso del formato .json para el almacenamiento a .ndjson, de esta manera podemos agregar los registros al final sin reescribir todo el archivo.
        \item El archivo ya no se carga en memoria, se streamea el cliente directamente desde disco en batches. Destacamos que agregamos los caracteres [ al inicio y ] al final del stream para mantener la firma original con respecto al formato .json.
        \item Solo enviamos hasta el último byte válido disponible al momento de recibida la consulta y verificamos que la última entrada sea válida (evita race condition con la escritura).
        \item Exchange api loguea directamente al nuevo nodo dedicado mediante una conexión TCP dedicada.
    \end{itemize}

    \subsection{Impacto en los QA}
    \label{sec:propuesta_1_impacto_en_los_qa}

        \subsubsection{Performance}
        \label{sec:propuesta_1_performance}

        Es el QA que la propuesta busca mejorar. Al mover el log a un nodo dedicado, la serialización y el envío del log
        completo dejan de ejecutarse en el mismo proceso (y el mismo event loop) que atiende \texttt{/exchange}, por lo que
        la latencia de las operaciones de negocio deja de depender del tamaño del log. Además, el nodo de logs ya no mantiene
        el log en memoria ni lo reescribe completo cada 1s: agrega cada registro al final del archivo y lo lee desde disco
        en streaming al ser consultado.

        Como se verá en las pruebas de estrés (Sección~\ref{sec:propuesta_1_pruebas_de_stress}), la latencia de \texttt{/exchange}
        se mantiene estable mientras \texttt{/log} se degrada
        (Figura~\ref{fig:comparacion_propuesta_1_sistema_base_stress_endpoint_response_time}). Por otro lado, la consulta del log
        sigue siendo $\mathcal{O}(n)$ sobre la cantidad de operaciones, por lo que \texttt{/log} continúa degradándose con el tiempo, y los
        percentiles altos vistos desde el cliente empeoran al procesarse más operaciones.

        \subsubsection{Disponibilidad}
        \label{sec:propuesta_1_disponibilidad}

        La degradación del log ya no arrastra a los endpoints de negocio: en el escenario de resistencia el sistema base
        comenzaba a fallar en el minuto 20, mientras que la propuesta 1 completó todas las requests durante los 45m
        (Figura~\ref{fig:comparacion_propuesta_1_sistema_base_soak_requests_state}).

        Sin embargo, se agrega una nueva dependencia en el arranque: la API de exchange no comienza a atender requests hasta
        conectarse con el nodo de logs, y reintenta indefinidamente cada 1s. Si el nodo de logs no está disponible, la
        API tampoco lo está. Una vez iniciada, en cambio, una caída del nodo de logs no detiene a la API de exchange.

        \subsubsection{Confiabilidad}
        \label{sec:propuesta_1_confiabilidad}

        El nuevo formato mejora la persistencia del log: cada registro se agrega al final del archivo en lugar de reescribir el
        archivo completo cada 1s, lo que elimina la ventana en la que un fallo durante la escritura corrompía todo el log (Código~\ref{lst:save}).
        La consulta solo envía hasta el último byte escrito al momento de recibirla y descarta una línea incompleta, por lo que
        el cliente siempre recibe un JSON válido.

        Como contrapartida, el envío del registro es \textit{fire and forget}: la API de exchange escribe en el socket TCP y
        responde al cliente sin esperar confirmación de que el registro fue persistido. Además, la conexión se establece una
        única vez en el arranque y no hay reconexión: si el nodo de logs se cae o se reinicia, las operaciones se siguen
        confirmando al cliente pero dejan de registrarse en el log sin ningún aviso. Para un log de transacciones de una
        fintech, que puede ser necesario para auditoría, esto es un riesgo que debe resolverse (por ejemplo, con reconexión y un
        buffer local, o confirmando la escritura antes de responder, a costa de latencia).

        \subsubsection{Escalabilidad}
        \label{sec:propuesta_1_escalabilidad}

        El desacoplamiento permite asignar recursos de forma independiente a la API de exchange y al nodo de logs según la carga
        de cada uno: como se vio en el escenario de estrés, la API queda casi ociosa mientras el nodo de logs concentra el
        consumo (Figura~\ref{fig:comparacion_propuesta_1_sistema_base_stress_resources}). La API de exchange, en cambio, sigue
        sin poder replicarse, ya que mantiene las cuentas y las tasas en memoria (Sección~\ref{sec:impacto_en_la_escalabilidad}).

        El desacoplamiento es además una condición previa para escalar horizontalmente la consulta del log, pero la
        implementación actual no lo permite sin cambios. Replicar el nodo de logs requeriría:

        \begin{itemize}
            \item que las réplicas compartan el archivo (por ejemplo, mediante un volumen) o un almacenamiento externo, ya que
            actualmente el archivo vive dentro de cada contenedor;
            \item modificar la configuración de nginx, cuyo upstream apunta a un único contenedor (\texttt{exchange-log-api-1});
            \item modificar la API de exchange, que abre una única conexión TCP con el nodo de logs al arrancar, por lo que
            todas las escrituras llegarían a una sola réplica.
        \end{itemize}

        \subsubsection{Seguridad}
        \label{sec:propuesta_1_seguridad}

        El puerto TCP 3002 del nodo de logs acepta registros de cualquier cliente dentro de la red de Docker, sin autenticación
        ni validación del contenido. Cualquier contenedor comprometido podría insertar registros falsos en el log de
        transacciones, lo que afecta su integridad. El puerto no se publica al host y nginx solo expone \texttt{/log}, por
        lo que el riesgo queda acotado a la red interna.

        \subsubsection{Modificabilidad}
        \label{sec:propuesta_1_modificabilidad}

        Se separan responsabilidades que antes estaban mezcladas en \texttt{state.js} (Código~\ref{lst:acoplamiento}): la API de exchange ya no conoce cómo se
        almacena ni cómo se consulta el log, lo que permitiría cambiar el almacenamiento (por ejemplo, a una base de datos) sin
        tocarla. La interfaz pública de \texttt{/log} se mantiene sin cambios para los clientes. En contrapartida, el protocolo
        entre ambos nodos (JSON delimitado por saltos de línea sobre TCP) es ad hoc, y los nombres de host y puertos están
        fijos en el código y en la configuración de nginx.

        \subsubsection{Costo y simplicidad}
        \label{sec:propuesta_1_costo_y_simplicidad}

        Se agrega un contenedor con los mismos límites de recursos que la API (1 CPU y 4 GB de memoria), lo que duplica los
        recursos reservados. Según las mediciones, la API de exchange queda prácticamente ociosa, con un $14.2\%$ de CPU en el
        escenario de estrés (Figura~\ref{fig:comparacion_propuesta_1_sistema_base_stress_resources}), por lo que sus límites
        podrían reducirse. La arquitectura suma un componente y un conector nuevo, así como un orden de arranque a respetar,
        aunque la complejidad agregada es menor que la de la propuesta 2 (Sección~\ref{sec:propuesta_2_simplicidad}).

    \subsection{Pruebas de carga}
    \label{sec:propuesta_1_pruebas_de_baseline}

    Las pruebas de carga utilizan la misma configuración que en el sistema base (Sección~\ref{sec:sistema_base_pruebas_de_baseline}), de modo que los resultados sean comparables.
    Con esta carga y esta duración el log todavía es chico, por lo que no esperamos que la degradación del sistema base llegue a manifestarse; el efecto principal de la táctica se observa en los escenarios de estrés y resistencia.

    Ambos sistemas completaron todas las requests sin fallas, con un promedio de 385 requests completadas por ventana de 10s en la propuesta 1 y de 397 en el sistema base.
    La diferencia se debe a la primera ventana de la propuesta 1, que registra solo 38 requests por corresponder al inicio de la prueba; a partir de la segunda ventana ambos sistemas completan alrededor de 400.
    Los tiempos de respuesta de \texttt{/exchange} son equivalentes (P95 de 716ms frente a 718ms medido en el servidor, y P95 de 709ms frente a 712ms visto desde el cliente), ya que están acotados por las dos transferencias.

    La diferencia aparece en \texttt{/log}, cuyo P95 promedio se reduce a la mitad (3.61ms frente a 6.97ms, con un máximo de 11ms frente a 22ms), y en el uso de recursos de la API, cuyo CPU promedio baja del $9.28\%$ al $4.02\%$ y su memoria del $1.25\%$ al $0.81\%$, al dejar de mantener, serializar y persistir el log.
    El nodo de logs consume en promedio un $3.35\%$ de CPU, por lo que el consumo sumado de ambos nodos ($7.37\%$) es menor que el de la API del sistema base.
    Su memoria crece durante la prueba, del $0.5\%$ al $3.67\%$; en el escenario de resistencia se observa que este crecimiento se da en los primeros minutos y luego se estabiliza en torno al $5\%$, sin crecer con el tamaño del log (Figura~\ref{fig:comparacion_propuesta_1_sistema_base_soak_resources}).

    \subsection{Pruebas de caos}
    \label{sec:propuesta_1_pruebas_de_chaos}

    No ejecutamos el escenario de caos sobre la propuesta 1, ya que la táctica no modifica ninguno de los elementos que
    determinan su resultado en el sistema base (Sección~\ref{sec:sistema_base_pruebas_de_chaos}):

    \begin{itemize}
        \item la validación de \texttt{/exchange} en \texttt{app.js} sigue siendo por presencia (Código~\ref{lst:request_validation}),
        por lo que la request con la moneda inexistente \texttt{XXX} es aceptada;
        \item \texttt{exchange.js} sigue accediendo a \texttt{rates[baseCurrency][counterCurrency]} sin verificar que la moneda
        exista, lo que lanza una excepción;
        \item el handler de \texttt{/exchange} sigue siendo una función \texttt{async} sin \texttt{try/catch}, por lo que la
        excepción termina el proceso (Sección~\ref{sec:impacto_en_la_disponibilidad});
        \item el \texttt{docker-compose.yml} de la propuesta no agrega una política de reinicio ni un health check para la API.
    \end{itemize}

    Por lo tanto, esperamos el mismo resultado que en el sistema base: la API termina con la primera request inválida y no
    vuelve a atender requests durante el resto de la prueba. El nodo de logs no cambia este resultado, ya que la
    propuesta solo lo desacopla de las operaciones de negocio y no interviene en el procesamiento de \texttt{/exchange}.
    La recuperación frente a este tipo de fallas es el objetivo de la propuesta 2 (Sección~\ref{sec:propuesta_2}).

    \subsection{Resultados y conclusiones}
    \label{sec:propuesta_1_resultados_y_conclusiones}

    La propuesta 1 demostró ser capaz de aislar la degradación producida por la consulta de logs de las operaciones de negocio del sistema, permitiendo ofrecer una mejor disponibilidad a los usuarios comunes (Figura~\ref{fig:comparacion_propuesta_1_sistema_base_soak_requests_state}).
    Por otro lado, la consulta de logs sigue degradándose con el tiempo. El desacoplamiento es un primer paso para escalar
    horizontalmente la lectura del log, pero para lograrlo las réplicas del nodo de logs deberían compartir el almacenamiento,
    y nginx y la API de exchange deberían poder distribuir las lecturas y las escrituras entre ellas
    (Sección~\ref{sec:propuesta_1_escalabilidad}). Como se mencionó en la Sección~\ref{sec:propuesta_1}, la solución de fondo
    es paginar la consulta.
