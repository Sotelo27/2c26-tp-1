\section{Comportamiento del Servicio}
\label{sec:sistema_base}

    \subsection{Pruebas de carga}
    \label{sec:sistema_base_pruebas_de_baseline}

        La prueba de carga se realizó usando una tasa constante de 40 usuarios durante 240s (4m).
        Cada usuario realiza un solo request, es decir se mantiene un throughput constante de 40 requests/s.
        No se realizó warm-up ni ramp para no ensuciar las métricas de promedios.
        Tampoco se realizaron recargas de saldo intermedias, se utilizó una carga inicial suficiente para cubrir toda la prueba.

        Adicionalmente, aprovechando que siendo este el sistema inicial no se plantea una comparativa, decidimos usarla para ilustrar el formato de los gráficos y explicar los criterios compartidos entre todos los escenarios.

        Se pueden encontrar los resultados completos en el Apéndice (Sección~\ref{sec:resultados_completos_sistema_base_baseline}).

    \subsection{Pruebas de estrés}
    \label{sec:sistema_base_pruebas_de_stress}

        La prueba de estrés se realizó incrementando progresivamente la carga desde 40 hasta 180 en saltos de 20, cada salto con una duración de 45s, el tiempo total de la prueba es de 450s (7.5m).
        Se realizó un warm-up inicial de 5 usuarios durante 30s. Además, al final de la prueba se dejó una instancia de recovery de nuevamente 5 usuarios esta vez durante 60s.
        Tampoco se realizaron recargas de saldo intermedias y se simplifico el uso de endpoints dejando solo \texttt{/exchange}, \texttt{/log} y \texttt{/rates} luego de las conclusiones obtenidas en (Figura~\ref{fig:sistema_base_baseline_scenarios}).

    \subsection{Pruebas de caos}
    \label{sec:sistema_base_pruebas_de_chaos}

    El reparto de requests se mantiene igual que en la prueba de resistencia (Figura~\ref{fig:sistema_base_baseline_scenarios}).
    Adicionalmente se agrega una request malintencionada sabiendo que no hay un buen manejo de errores (Sección~\ref{sec:impacto_en_la_disponibilidad}).
    Este tiene una probabilidad suficiente para aparecer entre 2 o 3 veces a lo largo de la prueba.
    Cada usuario realiza un solo request, es decir se mantiene un throughput constante de 40 requests/s.
    No se realizó warm-up ni ramp porque no aportaban información relevante para esta prueba.
    Tampoco se realizaron recargas de saldo intermedias, se utilizó una carga inicial suficiente para cubrir toda la prueba.

    \label{sec:sistema_base_resultados_y_conclusiones}

    Los resultados obtenidos del escenario de carga nos indican que podemos clasificar los endpoints en tres categorías (Figura~\ref{fig:sistema_base_baseline_endpoint_response_time}) lo que nos permitirá simplificar nuestro análisis.
    Adicionalmente, los resultados del escenario de estrés (Sección~\ref{sec:sistema_base_pruebas_de_stress}) y resistencia (Sección~\ref{sec:sistema_base_pruebas_de_soak}) nos indican que el sistema presenta una degradación significativa por la mala gestión del log. Esta observación motivará la propuesta 1 (Sección~\ref{sec:propuesta_1}).
    Finalmente, los resultados del escenario de caos (Sección~\ref{sec:sistema_base_pruebas_de_chaos}) nos indican que el sistema base no provee mecanismos de recuperación. Esta observación motivará la propuesta 2 (Sección~\ref{sec:propuesta_2}).
